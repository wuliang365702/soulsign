# 调度关系说明

这份文档用于说明当前 `build_v2.5.15` 里：

- `check`
- `run`
- `@expire`
- `retry_freq`
- `loop_freq`

分别负责什么，以及它们在自动调度时是怎么配合工作的。

## 先记住一句话

- `check`：负责判断账号当前是否在线，必要时补登录
- `run`：负责执行真正的签到动作

推荐写脚本时按这个职责拆分：

- `check(param)` 只做在线判断，必要时登录
- `run(param)` 只做签到，不负责补登录

## 当前版的两层调度

当前版本的调度分成两层：

### 第一层：后台多久唤醒一次

主要在：

- [`service-worker.js`](../js/service-worker.js)

当前行为：

- 浏览器/扩展启动后，延迟一段时间触发一次
- 之后按 `loop_freq` 周期性触发

这里的 `loop_freq` 是：

- **任务循环频率（秒）**

也就是：

- 后台多久整体扫描一轮任务

### 第二层：这一轮扫描里，每个任务怎么判断

主要在：

- [`offscreen.js`](../js/offscreen.js) 的 `schedulerTick()`

这里会决定：

- 要不要重新 `check`
- 要不要执行 `run`
- 失败后是否允许重试
- 今天是不是已经算完成

## 自动调度的简化流程

每次调度器被唤醒后，大致会这样判断每个任务：

1. 任务是否启用  
未启用直接跳过

2. 当前时间窗口里是否已经完成  
如果今天已经成功，就跳过

3. 是否需要重新检查在线状态  
如果需要，就执行 `check()`

4. 如果 `check()` 结果是不在线  
标记离线，停止，不执行 `run()`

5. 如果在线，再判断这次是否到执行时机  
例如：
- 今天是否还没完成
- 是否已到失败后的重试时间

6. 条件满足后，才真正执行 `run()`

## `check` 和 `run` 的关系

### 自动调度时

自动调度一般会先依赖 `check`，再决定要不要 `run`。

所以推荐脚本写法是：

- `check` 负责在线和登录
- `run` 负责签到

### 手动立即执行时

手动点“运行”一般是直接执行 `run()`，不一定先 `check()`。

### 调试时

- 调试 `CHECK`：只执行 `check()`
- 调试 `RUN`：只执行 `run()`

所以如果你的 `run()` 不负责补登录，那么：

- 自动调度通常没问题
- 但手动调试 `RUN` 时，如果当前未登录，就可能直接返回“未登录”

这属于正常现象。

## `@expire` 是做什么的

`@expire` 表示：

- 在线状态可以缓存多久

也就是：

- 上次 `check()` 成功/失败之后，多久内可以复用这次在线状态
- 超过这个时间，再重新 `check()`

### 当前版规则

当前版是：

1. 脚本有 `@expire`
   - 优先使用脚本自己的值
2. 脚本没有 `@expire`
   - 回退到全局兜底值

主要代码位置：

- [`offscreen.js`](../js/offscreen.js) `getOnlineRecheckMs()`

### 例子

```js
// @expire 300e3
```

表示：

- 在线状态缓存 300000 毫秒
- 也就是 300 秒
- 即 5 分钟

这意味着：

- 5 分钟内不必重复 `check()`
- 超过 5 分钟后，下次调度会再次 `check()`

## `retry_freq` 是做什么的

`retry_freq` 表示：

- 一个任务失败后，至少隔多久才允许再次尝试执行

它影响的是：

- **失败后的重试**

不影响：

- 后台多久整体扫描一次

### 例子

如果：

- `retry_freq = 600`

表示：

- 任务 10:00 失败后
- 10:10 之前都不允许再次执行 `run()`

即使调度器这期间被唤醒，也会因为“还没到重试时间”而跳过。

## `loop_freq` 是做什么的

当前版里，`loop_freq` 已经改成真正的：

- **任务循环频率（秒）**

它控制的是：

- 后台多久整体扫描一轮任务

### 例子

如果：

- `loop_freq = 3600`

表示：

- 后台每 3600 秒
- 也就是每 1 小时
- 整体跑一次调度扫描

注意：

- 它不是在线状态缓存时间
- 在线状态缓存由 `@expire`（或兜底值）决定

## 一个完整例子

假设某脚本：

```js
// @expire 300e3
```

并且设置：

- `loop_freq = 3600`
- `retry_freq = 600`

那么大致行为是：

1. 后台每 1 小时扫描一次任务
2. 扫描到这个任务时：
   - 如果今天已经签到成功，直接跳过
   - 如果今天还没成功，再看上次在线检查时间
3. 因为 `@expire = 300e3`
   - 超过 5 分钟没检查在线状态，就重新 `check()`
4. 如果 `check()` 不在线
   - 标记离线，不执行 `run()`
5. 如果在线
   - 再判断是否到重试时间
6. 如果上次失败距今超过 600 秒
   - 才允许再次执行 `run()`

## 最推荐的脚本写法

推荐把脚本写成：

```js
exports.check = async function (param) {
  // 负责判断是否在线，不在线时补登录
  return true;
};

exports.run = async function (param) {
  // 只负责签到
  return "签到成功";
};
```

推荐原因：

- 逻辑清楚
- 自动调度更容易配合
- 失败排查也更容易判断是“登录问题”还是“签到问题”

## 一句话总结

- `loop_freq`：多久整体扫描一轮任务
- `@expire`：在线状态多久后重新 `check`
- `retry_freq`：失败后多久允许再次 `run`
- `check`：在线判断/补登录
- `run`：真正签到
